# Test Audit — bpmn-audit

---

## Критические проблемы

### 1. Тесты проверяют копии функций, а не продакшн-код

Оба файла явно указывают это в комментариях:

- `AgreementBugFixTest.php`, строки 14–17: «Копии исправленных функций (автономно, без подключения updateAgreement.php, который выполняет запросы к БД при подключении)»
- `AgreementBugFixIntegrationTest.php`, строки 34–35: «Копии чистых функций из modules/documents/ajaxHandlers/updateAgreement.php»

Это означает: если разработчик исправит баг в `updateAgreement.php` неправильно, но при этом не обновит копию в тестах — все тесты продолжат проходить. Тесты защищают копию кода, а не рабочий файл. Это главная структурная проблема обоих файлов.

### 2. Нет ненулевого кода выхода при провале тестов

Функция `printReport()` в обоих файлах выводит текст «ЕСТЬ ОШИБКИ» при наличии провалившихся тестов, но **никогда не вызывает `exit(1)`**. При любом результате процесс завершается с кодом 0. В любой CI-системе или автоматическом запуске это означает, что провалившиеся тесты невидимы — пайплайн считает прогон успешным.

### 3. Группа 5 — симуляция из 230 строк вместо проверки реального кода

Метод `simulateGetDocumentStatusForIcon()` (`AgreementBugFixTest.php`, строки 1159–1391) — это полное переписывание функции `getDocumentStatusForIcon()` из `modules/documents/pages/index_ajax.php`. Это не тест продакшн-кода, а отдельная реализация той же логики. Если в симуляции присутствуют те же ошибки, что и в оригинале, тесты пройдут, а баги останутся. Если симуляция и оригинал разойдутся в деталях, тесты будут давать ложные результаты в обоих направлениях.

### 4. Группа 4 — вспомогательные методы тестируют сами себя

Методы `roadmapCountSigners()` и `roadmapCountResults()` (строки 928–971) определены прямо в тест-классе. Они не вызывают никакой код из `modules/roadmap/ajaxHandlers/updateAgreement.php` — они тестируют логику, написанную внутри самого тестового класса. Тест 4.10 проверяет отсутствие строки в файле через `strpos` — это единственная проверка реального продакшн-кода в группе 4.

## Важные замечания

### 5. Нулевое покрытие для багов 4, 5, 6 из bug-b-analysis.md

`bug-b-analysis.md` описывает шесть багов. Тесты покрывают только Баги 1 и 2. Следующие три совсем не покрыты:

- **Баг 4** (`collectGlobalStats`): функция не рекурсирует в `redirect[]` глубже одного уровня — статус C в цепочке A→B→C не учитывается в глобальной статистике. Нет ни одного теста.
- **Баг 5** (`applySignsToAgreementList`): подписи из `cam_signs` применяются только на первом уровне `redirect[]`, подпись участника C не синхронизируется. Нет ни одного теста.
- **Баг 6** (уведомления): участник B не получает уведомление после решения C, потому что для него не создаётся `_is_redirector_repeat`-запись (следствие Бага 2). Нет ни одного теста.

### 6. Нет тестов для клиентского JS-кода

`bug-a-analysis.md` локализует значительную часть бага А в JS-функции `applyUserAction` в файле `modules/documents/dialogs/agreement.php` (строки 319–328). Весь клиентский поток согласования остаётся без тестового покрытия. Ни unit-тестов (например, через Jest), ни интеграционных тестов браузерного поведения нет.

### 7. Не покрыта проблема двойных вхождений в `$allFound`

`status-indicator-analysis.md`, проблема 1: при определённых структурах agreementList пользователь может попасть в `$allFound` дважды — один раз через основной цикл, второй через `$findUserInAllRedirects`. Этот сценарий не тестируется ни в одной группе.

### 8. Интеграционные тесты работают с продакшн-БД

`AgreementBugFixIntegrationTest.php` подключается к реальной базе данных через SSH-туннель. Использование маркера `TEST_SOURCE_TABLE = 'test_bug_fix'` и блока `finally` — правильный подход. Однако если операции вставки триггерят каскадные записи в другие таблицы (например, `cam_tasklog`, `cam_notifications`), эти записи не будут очищены. Риск невысокий, но стоит зафиксировать.

## Мелкие замечания

### 9. Слабые assertions в группе 5

Тест 5.1 проверяет: `$result['color'] !== 'var(--color_02)'` — отрицательный assertion. Проходит при любом значении, кроме серого: при `null`, при неожиданной строке, при значении по умолчанию. Должен проверять конкретный ожидаемый цвет: `=== 'var(--blue)'`.

Тест 5.1 содержит два разных assertion с одинаковым названием `'Тест 5.1: ...'` — это затрудняет диагностику при провале.

### 10. Неполное покрытие вариантов нормализации `_is_redirector_repeat`

Группа 2 проверяет `_is_redirector_repeat: true` (boolean) и `'true'` (строка). Функция `normalizeSection` обрабатывает также `1` (int) и `'1'` (строка), но для этих вариантов тестов нет.

### 11. Нет теста для глубины цепочки 3+

Группа 3 тестирует цепочку A→B→C (2 уровня). Нет теста для A→B→C→D (3 уровня), хотя функция `_insertRepeatInLevel` рекурсивна и теоретически должна работать на любой глубине.

### 12. Нумерация тестов в группе 1.4/1.5 нарушена

В методе `testGroupApplySigns()` тест с двумя разными участниками (id=11, id=22) содержит assertions с именами «Тест 1.4» и «Тест 1.5», тогда как они находятся внутри одного сценария с одной структурой `$agreementList`. Это не ошибка логики, но нарушает читаемость: «Тест 1.5» не является независимым сценарием.

### 13. Изоляция unit-тестов — в целом соблюдена, одно исключение

`AgreementBugFixTest.php` не подключается к БД и не обращается к внешним сервисам — это правильно для unit-тестов. Единственное исключение: тест 4.10 читает реальный файл с диска через `file_exists()` / `file_get_contents()`. При переносе тестов в другое окружение или при отсутствии файла `modules/roadmap/ajaxHandlers/updateAgreement.php` тест либо упадёт, либо даст ложноположительный результат (пустая строка не содержит искомой подстроки → тест проходит).

### 14. Пустой `$message` при успехе не используется

Параметр `$message` в методе `assert()` передаётся только при провале теста. При успехе он игнорируется. Тем не менее часть вызовов передаёт в `$message` строку с позитивным описанием (например, «INSERT выполнен, id=...»), которая никогда не выводится.

## Непокрытые сценарии

1. **collectGlobalStats не считает C в цепочке A→B→C** — Баг 4 из bug-b-analysis.md. Нужен тест, симулирующий `collectGlobalStats()` с трёхуровневой структурой и проверяющий корректность счётчиков `pending`/`approved`.

2. **applySignsToAgreementList не синхронизирует подпись C** — Баг 5 из bug-b-analysis.md. Нужен тест: в `cam_signs` есть запись для id=C, redirect-цепочка A→B→C, после `applySignsToAgreementList` у C должен быть result.

3. **Уведомление B после решения C** — Баг 6 из bug-b-analysis.md. Сложно тестировать без мока, но можно проверить структурно: после `insertRedirectorRepeatEntry` в `A.redirect[]` должна появиться `_is_redirector_repeat`-запись для B — и это значит, что `sendNotificationsToNextActors` сможет найти B.

4. **Двойное вхождение в `$allFound`** — проблема 1 из status-indicator-analysis.md. Нужен тест: пользователь одновременно в основном списке и в `redirect[]` одной секции; убедиться, что приоритетная сортировка выдаёт ожидаемый результат.

5. **`_is_redirector_repeat` как int `1` и строка `'1'`** — дополнить тесты группы 2 двумя сценариями.

6. **Цепочка глубиной 3: A→B→C→D** — проверить, что `insertRedirectorRepeatEntry` и `isRedirectChainCompleted` корректно обрабатывают три уровня вложенности.

7. **`isRedirectChainCompleted` с `result.id=5` (rejected) у промежуточного участника** — должна ли цепочка считаться завершённой? Текущая реализация возвращает `true` для `rejected`, но нет теста, явно проверяющего это граничное условие.

8. **Тест реального кода `updateAgreement.php`** — хотя бы один тест должен подключать реальный файл (или его автозагружаемую версию) и вызывать производственные функции напрямую, а не их копии.

---

## Вывод

Тесты написаны аккуратно и демонстрируют понимание бизнес-логики системы согласования. Читаемость хорошая: названия тестов информативны, структура групп логична. Однако с точки зрения реальной защитной ценности тесты имеют фундаментальный изъян: они тестируют изолированные копии функций, а не производственный код. Изменение в `updateAgreement.php` не вызовет провала ни одного теста до тех пор, пока разработчик не синхронизирует копии вручную.

Дополнительно отсутствует `exit(1)` при провале, что делает тесты бесполезными в автоматизированной среде. Три из шести багов, описанных в `bug-b-analysis.md`, не имеют ни одного теста. Клиентская JS-логика не покрыта вообще.

**Оценка:** тесты полезны как живая документация ожидаемого поведения и как инструмент ручной проверки при запуске разработчиком. Как защитный механизм от регрессий — слабые.
