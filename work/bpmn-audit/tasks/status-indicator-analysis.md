# Анализ: цветовая индикация статусов в листинге документов

## Текущая реализация

### PHP-бэкенд (`modules/documents/pages/index_ajax.php`)

Цветовая индикация полностью формируется на сервере в цикле вывода строк таблицы (строки ~1252–1390).

**Используемая функция:** `getDocumentStatusForIcon(int $userId, ?string $agreementListJson, int $documentStatus, int $docId)` — строки 245–1087.

**Последовательность обработки для каждой строки:**

1. Вызов `getDocumentStatusForIcon()` → возвращает массив: `icon_class`, `color`, `status_type`, `status_text`, `can_approve`, `title`.
2. Вызов `validateSignersCount()` → проверяет корректность структуры подписантов.
3. Формирование CSS-классов и стиля на основе `status_type` и `color`:
   - `rejected` / `document_rejected` → класс `redText`, красный цвет
   - Невалидная структура подписантов → иконка `warning`, оранжевый
   - `status == 1` ИЛИ `icon_class == 'task_alt'` → зелёный, иконка `task_alt`
   - Иначе: `color == 'var(--color_02)'` → класс `grey`; любой другой цвет → класс `blue`

**Итоговый HTML-вывод (строка 1364):**
```html
<td class="status {$class}" title="{$agrStatus['title']}">
    <span class="material-icons {$class}" style="color:{$agrStatus['color']}">{$icon}</span>
    {$statusText}
</td>
```

### JavaScript-клиент (`modules/documents/js/registry_items.js`)

Никакой цветовой логики нет. JS отвечает только за:
- Открытие диалогов согласования (`.agreementDoc`, строки 111–116)
- Открытие PDF-просмотра (`.viewDoc`, строки 106–110)
- Инициализацию фильтров, сортировки, DaData

Цвет строки устанавливается исключительно сервером при генерации HTML.

## Причина комментирования `getDocumentStatusForIcon()` (строки 27–150)

Старая (закомментированная) функция имела **принципиально другую логику**: она анализировала только прямое вхождение пользователя в `agreementlist`, без учёта:
- перенаправлений (`redirect[]`)
- `_is_redirector_repeat` — повторной записи перенаправившего
- подписей из таблицы `cam_signs`
- многоуровневых цепочек redirect

Функция была заменена новой реализацией (строки 245–1087), которая:
- Ищет пользователя рекурсивно по всему дереву (основной список + все вложенные `redirect[]`)
- Собирает **все вхождения** пользователя (`$allFound`) и выбирает приоритетное
- Загружает подписи из `cam_signs` для дополнительной верификации
- Обрабатывает незавершённые цепочки redirect

Старая функция была закомментирована как мёртвый код после полного переписывания, но физически не удалена (очевидно, для истории или сравнения).

## Расхождение с ожидаемым поведением

### Ожидаемое поведение
- **Синий** — текущий пользователь является **active target** в цепочке согласования (его очередь)
- **Серый** — не его очередь (ждёт других)
- При перенаправлении: если пользователь является `target` в активной redirect-цепочке → синий

### Выявленные проблемы

#### 1. Двойное вхождение через `$findUserInAllRedirects` и основной цикл

Функция `$findUserInAllRedirects` (строки 359–401) ищет пользователя ТОЛЬКО внутри `redirect[]`-массивов, но **игнорирует** записи на основном уровне. Одновременно основной цикл (строки 487–508) ищет только на первом уровне секции. Это может привести к дублированию — пользователь попадает в `$allFound` дважды (один раз через основной цикл, второй через `$findUserInAllRedirects`), если его id встречается и в списке первого уровня, и в `redirect[]` той же секции.

Приоритетная сортировка `$allFound` (строки 561–606) должна выбрать нужное, но логика сложная и потенциально ломается в крайних случаях.

#### 2. Проблема при redirect: пользователь является target, но его нет в основном списке

Структура `redirect[]` — это вложенный массив участников внутри объекта перенаправителя. Когда Пользователь A перенаправляет Пользователю B:
```json
{
    "id": A,
    "result": {"id": 4},
    "redirect": [{"id": B, "result": null}]
}
```

`$findUserInAllRedirects` находит B с `is_redirect = true` и статусом `pending`. Это обрабатывается в `case 'redirected'` (строки 709–923) через `$userPendingInRedirect` — и корректно возвращает синий цвет.

**НО:** `case 'redirected'` срабатывает, только если `$getApproverStatus` для `$userInfo['approver']` вернул `'redirected'`. Когда пользователь найден через `$findUserInAllRedirects`, его `$userInfo['approver']` — это его **собственная запись** внутри `redirect[]`, которая имеет `result = null` → статус `'pending'`, а не `'redirected'`.

Следовательно, управление переходит в `case 'pending'` (строка 926), где проверяется `$canAct`. Для записи внутри `redirect[]`:
- `is_redirect = true`
- `section` — это `redirect[]`-массив перенаправителя, а не основная секция
- `index` — позиция внутри `redirect[]`, а не в основном списке

Проверка предыдущих участников (`$userInfo['list_type'] == 1 && $userInfo['index'] > 0`, строки 937–950) проводится по `$userInfo['section']`, которая является `redirect[]`-массивом. Если у перенаправителя структура `redirect` не имеет `[0]` как метаданных секции, то `array_slice($userInfo['section'], 1)` может вернуть весь массив либо неправильный срез, и `$canAct` может быть некорректно вычислен.

#### 3. Проверка `$canAct` для redirect-получателей использует секцию redirect, а не основную секцию

При последовательном согласовании (`list_type == 1`) код проверяет, согласовали ли все **предыдущие** в `$userInfo['section']`. Для участников, найденных через `$findUserInAllRedirects`, `section` — это внутренний `redirect[]` перенаправителя. В нём нет метаинформации (`[0]` с `stage`, `list_type`) — только записи участников. Это означает:
- `$userInfo['list_type']` берётся из `$sectionInfo['list_type']`, а `$sectionInfo` — это `$section[0]` родительской секции, откуда пришёл redirect. Для одноуровневых перенаправлений это может работать случайно правильно.
- `$userInfo['index']` — это индекс внутри `redirect[]`, начиная с 0. Если redirect содержит несколько участников с последовательным согласованием, индексация может быть неверной (с поправкой на возможное отсутствие мета-элемента [0]).

#### 4. Условие для синего цвета при завершённом redirect (строки 813–847)

Когда redirect-цепочка завершена и пользователь **не** согласовал в ней сам (`!$userApprovedInRedirect`), система проверяет `$canActAfterRedirect` через `$userInfo['index']` и `$userInfo['section']`. Но `$userInfo` здесь — это запись **перенаправителя** (выбрана как приоритетная в `$allFound`). Её `section` — основная секция, `index` — позиция перенаправителя. Это поведение корректно только если перенаправитель и тот, кому должны действовать — одно и то же лицо. При цепочке A → B → C (где C — текущий пользователь) данная логика может некорректно определить, может ли C действовать сейчас.

## Предлагаемый фикс

### 1. Немедленно: удалить закомментированную старую функцию (строки 27–150)
Мёртвый код, вводит путаницу. Можно безопасно удалить.

### 2. Немедленно: удалить DEBUG-вывод для документа 181 (строки 476–478, 504–516, 610–628, 638–640, 710–713, 927–930)
Эти блоки генерируют HTML-комментарии в продакшн-выводе.

### 3. Исправить обработку записей из `$findUserInAllRedirects` в `case 'pending'`

Когда пользователь найден через `$findUserInAllRedirects` (`is_redirect = true`) и его `$userStatus['status'] == 'pending'`, нужно дополнительно проверить:
- Завершил ли перенаправитель своё действие (его `result.id == 4` и redirect получен корректно)
- Все ли предыдущие в **основной** секции согласовали до перенаправителя

Вместо использования `$userInfo['section']` (которая является `redirect[]`) для проверки предшественников, нужно искать **основную секцию**, в которой находится перенаправитель, и проверять предшественников относительно неё.

Конкретное место изменения — строки 934–951 (`case 'pending'`, блок проверки `$canAct`):

```php
// Для записей внутри redirect: проверяем не redirect-секцию, а основную
if ($userInfo['is_redirect'] && $userInfo['list_type'] == 1) {
    // Нужно найти основную секцию, где находится parent_approver,
    // и проверить его предшественников
    // ... логика поиска parent_approver в $data ...
}
```

### 4. Добавить поддержку случая: target redirect-а не в основном списке

Текущий `$findUserInAllRedirects` корректно находит такие записи, но механика `case 'pending'` не учитывает, что для участника внутри `redirect[]` "его очередь" определяется не его позицией в `redirect[]`, а тем, завершено ли перенаправление (все предыдущие в основной очереди согласовали, перенаправитель выполнил redirect).

Рекомендуется выделить отдельный `case` или условие для `is_redirect === true` в начале блока `if ($userFound)`.

### 5. Проверить раскомментирование старой функции
Старую функцию **раскомментировать нельзя** — она несовместима с текущей структурой данных (не принимает `$docId`, не работает с `cam_signs`, не обрабатывает `redirect[]`). Она должна быть удалена.
