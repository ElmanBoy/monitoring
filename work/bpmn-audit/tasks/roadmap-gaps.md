# Анализ расхождений модуля Roadmap со схемой BPMN

## Процесс дорожных карт по BPMN

Процесс описан в файле `IGNORE/Sheme.bpmn` (элементы Activity_0ey6b1b — Activity_01zp3hr).

Полная цепочка шагов:

1. **[Условие] Нарушения выявлены?** (`Gateway_0ey6b1b`)
   - ДА → шаг 2
   - НЕТ → шаг 6 (Доклад напрямую)

2. **Формирование дорожной карты по устранению нарушений** (`Activity_15w4kjb`)
   - Аннотация в схеме: _"Формирует учреждение"_
   - Аннотация: _"Предлагается сделать электронную дорожную карту с возможностью приложения подтверждения устранения пункта ДК и функционала согласования устранения сотрудником министерства"_

3. **Согласование ДК** (`Activity_0f7moma`)

4. **Устранение нарушений** (`Activity_00m2qpq`)
   - Также является целевым шагом после продления сроков

5. **[Условие] Все пункты ДК выполнены?** (`Gateway_0seypse`)
   - ДА → шаг 6 (Доклад)
   - НЕТ → шаг 5а (Продление сроков ДК)

5а. **Продление сроков ДК** (`Activity_1hchb8z`)
   - После продления возврат на шаг 4 (Устранение нарушений)

6. **Доклад** (`Activity_0g8zhi2`)
   - Принимает оба потока: из ветки "Нарушений нет" и из ветки "Все пункты выполнены"

7. **Результаты проверки включены в реестр** (`Activity_01zp3hr`)
   - Запись в `DataStoreReference_1j7ueee` — "Реестр результатов проверки"

8. **КОНЕЦ** (`Event_1iq53rh`)

Участники: схема не содержит явных pool/lane-разграничений, но по аннотации ясно: ДК формирует **учреждение (ОК)**, согласование и снятие нарушений — **министерство**.

## Что реализовано

### Шаг 1. Выявление нарушений
**Реализован.** Нарушения хранятся в `cam_checksviolations` и попадают в доклад (`documentacial=8`) через диалог `modules/documents/dialogs/create_report.php` — инспектор выбирает нарушения из чек-листа чекбоксами (`params[violation_ids][]`). Из согласованного доклада предложения переносятся в форму создания ДК.

Файлы:
- `modules/documents/dialogs/create_report.php` (строки 221–225)
- `modules/documents/ajaxHandlers/create_report.php` (строки 40–43)

### Шаг 2. Формирование дорожной карты учреждением
**Реализован.** ДК создаётся через диалог `modules/roadmap/dialogs/add_road.php`. Предложения по устранению берутся из согласованного доклада (`documentacial=8, status=1`) автоматически — ОК заполняет действия, сроки и ответственных. Кнопка создания ДК доступна только при наличии согласованного доклада.

Файлы:
- `modules/roadmap/dialogs/add_road.php`
- `modules/roadmap/ajaxHandlers/add_road.php`
- `modules/roadmap/pages/index_ajax.php` (строки 296–309)

### Шаг 4. Устранение нарушений (подтверждение ОК)
**Реализован.** В диалоге `modules/roadmap/dialogs/view_road.php` ОК (role=5) прикрепляет файлы-подтверждения и комментарий, нажимает "Отправить" — статус строки меняется на `fix_status=1` ("На проверке"). Министерство снимает нарушение (`fix_status=2`) или возвращает на доработку (`fix_status=3`).

Статусы строк графика:
- `0` — не устранено
- `1` — на проверке
- `2` — снято
- `3` — возврат на доработку

Файлы:
- `modules/roadmap/dialogs/view_road.php`
- `modules/roadmap/ajaxHandlers/update_road.php`

### Шаг 5а. Продление сроков пункта ДК
**Реализован** (на уровне отдельной строки, а не всей ДК). Министерство может нажать кнопку "Продлить" напротив конкретной строки. Вводится новая дата и причина. Сохраняется в поле `deadline_extended` строки JSONB.

Файлы:
- `modules/roadmap/ajaxHandlers/update_road.php` (строки 137–160, case 'extend')
- `modules/roadmap/dialogs/view_road.php` (строки 279–285, кнопка btn-fix-extend)

### Визуальный прогресс и индикация просрочки
**Реализован.** В списке и в диалоге просмотра отображается прогресс-бар, количество устранённых/просроченных строк, подсветка красным при просрочке.

Файлы:
- `modules/roadmap/pages/index_ajax.php` (строки 86–110, 216–252)
- `modules/roadmap/dialogs/view_road.php` (строки 35–43, 147–164)

### Итоговая фиксация результатов проверки
**Реализован** (в виде отдельного диалога `finalize_inspection`). Фиксирует тип результата, итоговое заключение, дату — сохраняет в таблицу `cam_inspectionresults`. Используется как финальная точка процесса проверки.

Файлы:
- `modules/roadmap/dialogs/finalize_inspection.php`
- `modules/roadmap/ajaxHandlers/finalize_inspection.php`

## Что не реализовано / реализовано иначе

### Расхождение 1: Шаг "Согласование ДК" отсутствует
По BPMN после формирования ДК (`Activity_15w4kjb`) следует явный шаг **Согласование ДК** (`Activity_0f7moma`) перед началом устранения нарушений.

В коде: граф устранения (`documentacial=5`) создаётся напрямую, у него нет поля `status` в контексте согласования — только прогресс устранения строк. Диалог `agreement.php` в модуле roadmap открывается для актов (`documentacial=2`) и для переписки по возражениям. Отдельного процесса согласования ДК (со списком согласующих, подписями) нет.

Для возражений ОК есть поле `documentacial=5` + кнопка "Направить возражения" (`agreementDoc`), но это не равнозначно шагу "Согласование ДК" из BPMN.

### Расхождение 2: Продление сроков — на уровне строки, не всей ДК
По BPMN шаг `Activity_1hchb8z` называется **"Продление сроков ДК"** (всей дорожной карты), после чего процесс возвращается на "Устранение нарушений" как единый цикл.

В коде: продление реализовано только для отдельной строки графика (`deadline_extended` в JSONB). Нет механизма продления срока всей ДК как документа — не меняется ни общий дедлайн документа, ни его статус. Нет истории продлений на уровне ДК, нет уведомлений при истечении общего срока.

### Расхождение 3: Автоматический переход "Все пункты выполнены → Доклад" отсутствует
По BPMN: шлюз `Gateway_0seypse` ("Все пункты ДК выполнены?") → при ДА автоматически запускается шаг "Доклад".

В коде: система отображает что все нарушения устранены (зелёный баннер в `view_road.php`, строки 147–149), но никакого автоматического перехода или создания Доклада не происходит. Пользователь должен вручную перейти к созданию итогового доклада. Связи между завершением ДК и созданием итогового доклада нет.

### Расхождение 4: Связь с нарушениями из чек-листов — косвенная, без violation_id
По BPMN предполагается прямая связь нарушения из чек-листа → пункт ДК.

В коде: при создании ДК поле `violation_id` в каждой строке JSONB заполняется пустым значением `""` (строка 162, `dialogs/add_road.php` — `value=""`). Нарушения попадают в ДК как **текст предложений из доклада**, а не прямые ссылки на записи `cam_checksviolations`. Это разрывает возможность трассировки: нарушение из чек-листа → строка ДК → статус устранения.

### Расхождение 5: Шаг "Результаты проверки включены в реестр" — реализован в отдельной таблице без интеграции
По BPMN: `Activity_01zp3hr` записывает данные в "Реестр результатов проверки" (`DataStoreReference_1j7ueee`).

В коде: диалог `finalize_inspection` сохраняет в `cam_inspectionresults`, но эта таблица не отображается нигде в интерфейсе модуля Roadmap — нет страницы просмотра реестра результатов, нет экспорта. Таблица `cam_inspectionresults` есть только в коде `finalize_inspection.php`, в схеме БД (`structure.sql`) её наличие нужно проверить отдельно.

### Расхождение 6: Нет триггера открытия ДК из модуля documents/tasks
По BPMN: ДК создаётся в контексте конкретной проверки. В системе: ДК привязана только к акту (`source_id`), но из модуля tasks или calendar нет прямой кнопки "Создать ДК". Весь процесс ведётся в модуле roadmap отдельно.

## Задачи на доработку

### Задача 1: Добавить согласование ДК (шаг "Согласование ДК" из BPMN)
- **Описание расхождения**: После создания ДК учреждением нет шага согласования со стороны министерства. График устранения сразу доступен для заполнения.
- **Ожидаемое поведение по схеме**: ДК должна проходить согласование (список согласующих, подписи). Только после согласования ДК учреждение начинает устранять нарушения.
- **Файлы для изменения**:
  - `modules/roadmap/ajaxHandlers/add_road.php` — добавить `status=0` при создании и шаблон agreementlist
  - `modules/roadmap/dialogs/view_road.php` — добавить блок согласования (аналогично `modules/documents/dialogs/agreement.php`)
  - `modules/roadmap/pages/index_ajax.php` — учитывать статус согласования при отображении кнопок

### Задача 2: Реализовать продление сроков всей ДК
- **Описание расхождения**: BPMN предусматривает продление ДК как единицы (возврат на "Устранение нарушений" целиком). Сейчас продление только по строке.
- **Ожидаемое поведение по схеме**: Если не все пункты выполнены, министерство продлевает срок всей ДК — фиксируется общий новый срок, причина, история продлений.
- **Файлы для изменения**:
  - `modules/roadmap/ajaxHandlers/update_road.php` — добавить действие `extend_all` (или отдельный handler)
  - `modules/roadmap/dialogs/view_road.php` — кнопка "Продлить ДК" для общего срока
  - Таблица `cam_agreement` или отдельное поле — хранить общий срок ДК и историю продлений

### Задача 3: Автоматический переход "Все пункты выполнены → инициировать Доклад"
- **Описание расхождения**: Система показывает что все нарушения устранены, но не инициирует создание итогового доклада и не уведомляет ответственного.
- **Ожидаемое поведение по схеме**: При закрытии последнего пункта ДК (fix_status=2) система должна автоматически предложить создать итоговый доклад или отправить уведомление.
- **Файлы для изменения**:
  - `modules/roadmap/ajaxHandlers/update_road.php` — после case 'close' проверять `$done === $total`, если да — отправить уведомление и вернуть флаг в ответе
  - `modules/roadmap/dialogs/view_road.php` — при `$done === $total` показывать кнопку "Перейти к итоговому докладу"

### Задача 4: Заполнять violation_id при создании строк ДК
- **Описание расхождения**: Поле `violation_id` в строках ДК всегда пустое, связь с `cam_checksviolations` не устанавливается.
- **Ожидаемое поведение по схеме**: Каждая строка ДК должна ссылаться на конкретное нарушение из чек-листа для обеспечения полной трассировки.
- **Файлы для изменения**:
  - `modules/documents/ajaxHandlers/create_report.php` — сохранять `violation_id` в proposals внутри body доклада
  - `modules/roadmap/dialogs/add_road.php` — передавать violation_id в hidden-поле (строка 162, сейчас `value=""`)
  - `modules/roadmap/ajaxHandlers/add_road.php` — сохранять violation_id в JSONB строки

### Задача 5: Создать страницу реестра результатов проверок
- **Описание расхождения**: Данные `finalize_inspection` сохраняются в `cam_inspectionresults`, но нигде не отображаются и недоступны для просмотра/экспорта.
- **Ожидаемое поведение по схеме**: "Реестр результатов проверки" должен быть доступен как отдельный список/отчёт.
- **Файлы для изменения**:
  - Создать `modules/roadmap/pages/results_ajax.php` (или отдельный модуль)
  - Добавить вкладку/ссылку в навигацию модуля roadmap
